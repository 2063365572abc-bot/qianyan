# Qianyan — Product Requirements

产品方向依据 `scope.md`：可定制的个人管家底座优先，以长期目标跟进作为验收闭环。用户已统一批准本方案及默认值，当前据此开发；实际可用性逐项验收，不以批准替代运行证据。

## Product Promise

**“告诉我一次，我会记住、持续跟进，并把下一步安排清楚。”**

目标用户先是一个真实个人使用者；第一条自动观察 Demo 服务黑客松/个人项目。用户拥有设置和记忆控制权，可暂停管家。首版自主能力限定为内部计划维护与向本人通知。

## The Core Journey

1. 用户第一次打开网页，设定管家称呼、沟通方式、个人偏好、时区、联系时段和权限；保存后立即看到设置生效。
2. 对话交代目标，补足具体日期和完成标准；Agent 提议任务、依赖和下一步。用户确认初始计划一次，后续在既定权限内自主调整。
3. 无连接器的目标依赖内部任务与用户上报线下进展；连接 GitHub/Vercel 的目标自动观察事实。页面显示每项信息从哪里来、最后观察时间。
4. 用户关闭网页。云端持续检查到期跟进和数据源，记录 Evidence，核对完成条件，生成计划差异并自动维护下一步。
5. 出现重要变化、待决策或需行动的提醒，企业微信收到简洁消息。用户可回复文字，或点击详情进入手机网页完成稍后提醒、确认、纠正。
6. 第二天打开网页，看到当前目标、最近变化、仍在阻塞的事和下一步；可以查看并修改记忆，无需重述昨天。

## Look and Feel

用户已要求：结果清楚、管家感、不要一堆 Agent 日志。建议视觉为安静、清晰的工作台：浅色背景、深色正文、单一青绿强调色；失败红色、不确定琥珀色，同时配文字标记。中文优先系统字体，录制和评审切换英文。称呼用于标题和对话，不做头像动画或语音。

PC 双栏：左侧目标与当前计划，右侧对话与近期结果卡。手机单栏，优先显示通知对应事项与操作按钮。来源、时间、权限始终可见；技术运行日志放开发者诊断区，不进入普通用户流程。视觉建议待总方案确认，可修改而不改核心架构。

## Screens

| 页面 | 主要信息与动作 | 空/错状态 |
|---|---|---|
| Today / 首页 | 最值得处理的最多三件事、最近变化、对话入口 | 没目标时邀请交代第一件事；无新变化安静显示上次检查时间 |
| Goal / 目标详情 | 期限、任务依赖、完成标准、证据、下一步、暂停 | 来源失联显示“无法观察”，保留历史，不伪造最新进展 |
| Memory / 记忆 | 偏好和项目事实、来源、更新记录、编辑/遗忘 | 无记忆时说明“只记住你交代或有来源的事项” |
| Butler / 管家设置 | 称呼、风格、偏好、时区、通知、权限 | 未保存提示；渠道未连通显示配置状态 |
| Inbox / 跟进收件箱 | 待决策、通知结果、详情和稍后提醒 | 发送失败展示失败状态和重试入口 |
| Demo / 公开体验 | 独立样例空间、真实/回放标签、体验重置 | 网络/模型失败明确显示；不读取真实用户数据 |

可将前三项做成同一页面内的侧栏/面板，不要求六套复杂页面。URL 可分享某个目标和通知详情，但分享不绕过访问权限。

## Features and Behavior

### F1 — Customize Your Butler

对应 `scope.md > The Unique Kernel`。

- 称呼与简洁/细致、直接/温和的表达设置影响回复和通知文案。
- 个人偏好初版支持用户主动填写的工作时段、关注事项和禁止事项；未填写容量时不宣称计划一定能完成。
- 时区默认为 Asia/Shanghai；建议联系窗口 08:00–22:00，可修改。关闭主动通知与暂停目标可独立控制。
- 权限面板显示已开启：读取已连通数据源、维护内部计划、向本人通知。写代码、外部部署、发第三方消息等首版不可开启。
- 自定义风格不能扩大权限、覆盖事实核验或改变“未知”状态。

验收：保存并刷新仍存在；修改通知时段后后续跟进遵守新窗口；改变风格后相同事实的表达变化、事实与权限保持一致。

### F2 — Conversation and Goal Capture

对应 `scope.md > The Core Loop`。

- 文本对话和企业微信文字回复进入同一个个人空间。
- 目标包含名称、意图、期限、完成定义；“月底”“明天”须展示换算后的绝对日期和时区。日期含糊、截止规则不清时先问，不随意猜。
- 首次生成计划约三至八项任务，附依赖、完成标准、下一步和粗略时长；用户可以修改再确认。
- 建议容量：最多三个活动目标，每目标最多十项任务；超过时说明限制，不静默丢任务。
- 泛化目标如“本周把报名材料准备好”可使用内部状态和用户补充；首版不承诺系统能观察线下进展。

验收：交代一次目标后形成计划；对话续接能指向已有目标；初始计划没确认前不主动安排持续通知；相对日期显示绝对日期。

### F3 — Persistent, Editable Memory

对应 `scope.md > The POC Boundary`。

- 用户设置、明确表达的偏好、目标状态、项目事实、已确认决定与历史跟进长期保存。
- 每条记忆有类型、内容、来源、时间、适用目标与当前/已被替代状态。模型推测不能直接变成用户事实。
- 用户明确说“以后只在下午提醒我”可以写入并回显；潜在偏好先作为候选询问，不静默生成画像。
- 查看、编辑、遗忘、导出自己的记忆与计划。遗忘后相关旧摘要失效，下次模型上下文不再包含该信息；保留最小操作标识以保证运行一致性，不继续保留被遗忘正文。
- 第二天/服务重启后恢复个人设置、目标、计划和下一步。

验收：跨会话恢复；新偏好取代旧值；遗忘后检索和下一次回答不引用旧内容；导出不包含连接器密钥。

### F4 — Internal Plan and Progress Evidence

对应 `scope.md > The Unique Kernel`。

- 任务状态使用 Todo、In Progress、Blocked、Needs Review、Done、Skipped；取消与不做需要记录用户选择。
- 证据字段：Source、Evidence、Source URL/标识、Observed At、Source Updated At、关联版本、Confidence、适用完成条件。Confidence 为来源可信程度的分类，不展示伪精确概率。
- 观察与完成分离。事实和判断分别呈现；不可观察则显示 Unknown。
- 完成方式分为“明确客观规则满足”与“用户确认”。用户主观认可的核心功能完成、线下进展只能由用户确认。
- 新证据与旧证据冲突时保留事件历史；已失效的自动完成条件需要重新评估。用户确认的任务出现冲突时提示复核，不偷偷抹掉用户决定。

验收：文件出现本身不等于任务 Done；每个 Done 有当前规则证据或用户确认；来源不可用不新增完成结论；能够解释为什么仍未完成。

### F5 — Autonomous Follow-up and Replanning

对应 `scope.md > The Core Loop`。

- 触发来自定时跟进、真实事实变化、用户回复；关闭网页不影响运行。
- 自动调整内部状态、创建具体下一步、调整优先级、按依赖安排内部跟进。不得擅自改用户硬截止时间。
- 输出一张结果卡：发生什么、依据、计划改了什么、当前最高优先级、下一步、期限风险、需要用户回答什么。
- 无新事实且未到行动时间时只更新检查时间；不反复调用模型制造“进展”。相同阻塞只保留一个下一步，解决后同步收束该阻塞任务。
- 按任务依赖与预估时间讨论风险；缺少用户可投入时间时显示“信息不足/有风险”，不说“仍在计划内”作为事实。
- 支持暂停目标和恢复；支持撤销最近一次内部计划更新，保留事实证据，再按当前事实重新核对。暂停期间不积压重复通知。

验收：部署失败后排查优先、录制在成功部署后；重复观察不重复建任务；暂停后停止跟进；重启恢复到期工作；用户改优先级后下一次规划遵循。

### F6 — GitHub Observation

对应 `scope.md > The POC Boundary`。

首版选择一个 Repo、一个目标分支、一个指定 CI workflow，只读获取：Repo 存在、最新 commit/SHA、变更文件、README 与指定核心目录、CI 结果。默认五分钟轮询；可手动触发同一真实同步。CI 仅证明指定 workflow 在对应 SHA 的运行结果，跳过不等于测试通过。

README 客观标准建议由用户确认：简介、Installation、Usage 三个非空区块，Installation 有实际命令，Usage 有示例，忽略只有标题、空白和占位词的区块。满足结构规则可标记“README 结构完成”，不宣称语义质量完美或命令已经运行验证。

Issue/PR、Release/Tag 是扩展观察项，核心闭环通过且有余量后加入；第一版不依赖全套 GitHub 功能才可使用。

验收：空 Installation 不完成；完善后自动记录文件 SHA/证据并完成结构任务；旧 SHA 的成功 CI 不证明新 SHA 已通过；普通 commit 不推送。

### F7 — Deployment Observation

对应 `scope.md > The POC Boundary`。建议首版选择 **Vercel** 作为被观察平台；Qianyan 自身托管可在云服务器上，两者是不同配置。

只读获取绑定项目的生产部署、状态、时间、commit 关联与实际 Production URL；必要时读取失败 Build Log 的短片段或提供平台日志链接。不会替用户部署。

READY、生产域名、可访问性分别记录；Preview 不算 Production，构建成功不证明功能验收完成。最新候选构建失败时旧版本可能仍在线，必须区分“新部署失败”与“当前线上服务不可用”。网络检查失败可能是观察网络问题，不武断宣布服务宕机。

验收：生产构建失败创建阻塞并重排；后续成功可解除对应构建阻塞；旧线上版本仍可用时结果卡准确描述；URL 来源可追溯，不由模型生成。

### F8 — Proactive WeChat Contact

对应 `scope.md > Proactive Contact`。

- 第一版企业微信自建应用，真实向已绑定本人发消息，并接收本人文字回复；实际接收客户端明确标注。
- 三种通知：重要状态变化、需要用户决定、确需行动的提醒；Commit 和同步不推送。建议相近变化合并一分钟，同一原因一次，未处理的跟进至少间隔四小时且只在用户窗口发送；数值可改。
- 22:00–08:00 默认免打扰，所有消息尊重用户设置，不自动引入紧急绕过。设置关闭后仍维护内部计划。
- 消息至少包含目标、变化/依据、计划更新和下一步。链接进入手机网页提供详情、稍后提醒（建议两小时或自选）、我已处理、完成判断。
- “我已处理”记录用户声明，触发客观条件重新检查；需要平台证据的任务不因点击直接伪造 Success。用户仍标记完成时明确使用 User confirmation，并保留未通过的原条件。
- 原生交互卡按钮列为可选增强，不是最低验收要求。回调内容不明确指向目标/任务时询问确认，禁止猜错操作对象。

验收：关闭网页仍收到真实通知；文字回复能改变相应计划或提出澄清；重复事件不重复推送；免打扰延后发送；失效链接不执行旧动作；失败不显示已送达。API 接受发送只能标“平台已接受”，没有可靠回执时不标用户已读。

### F9 — Demo and Personal Data Separation

对应 `scope.md > What "Working" Looks Like`。

- 本人空间有基本登录保护；公开评审无需连接自己的微信或提供自己的 token。
- 每位评审获得隔离样例空间，用预置目标与证据回放理解变化；标记“样例/回放”。可调用真实 Nemotron生成计划解释，运行信息显示实际模型与数据模式。
- 真人录制展示真实 GitHub/Vercel 数据与企业微信收发、网页关闭后运行、跨日记忆。回放只压缩等待时间，不能用来声称真实后台触达已实现。
- 公共 Demo 不发送企业微信消息、不查看真实个人记忆、不执行对外操作；同一后端权限校验强制约束，不能依赖前端隐藏按钮。
- 英文界面/示例与中文界面共用功能；目标是完成不到三分钟的可复现演示。

验收：两个访客数据隔离；Demo 无本人消息权限；真实/回放明显标记；公开地址可访问，失败模式可解释。

## States and Boundaries

| 状态 | 用户看到什么 | 系统处理 |
|---|---|---|
| 首次使用/未接源 | 设置和第一个目标；来源未连接 | 可以使用内部目标，不制造外部事实 |
| 无变化 | 检查时间、既有下一步 | 不推消息，不重复重排 |
| 证据不足 | 缺项和待确认 | Needs Review 或原状态，保留依据 |
| Token/权限失效 | 来源暂不可用、上次成功同步时间 | 暂停该源结论，退避重试 |
| 模型失败/预算耗尽 | 自动规划暂不可用，已有事实和计划仍可读 | 不保存坏计划；确定性规则可更新客观状态，必要通知用事实模板 |
| 通知失败 | 网页保留收件项，渠道失败状态 | 有限重试，避免重复承诺送达 |
| 超期 | 明确超期、阻塞和可采取动作 | 提议缩范围/更改计划，不改硬截止 |
| 暂停/完成 | 状态明确，历史仍可查看 | 停止周期跟进；恢复时重新同步事实 |

## Product Decisions

用户已明确：可定制个人管家、底座优先、长期目标跟进、客观事实自动观察、主观进展由用户补充、内部计划自主维护、微信主动触达、首版可用企业微信、只在三类情况打扰。

实施建议待确认：React 工作台布局、浅色视觉、单人实例/隔离 Demo、三目标容量、Vercel 唯一部署观察源、上述通知默认值与 README 结构标准。

## What We're Building

F1–F5 组成通用底座；F8 提供关闭网页后的真实联系；F6–F7 构成第一条真实证据接入；F9 支撑公开评审。前三者都属于最终比赛 MVP，但开发先后顺序以底座优先。

## Deferred From the POC

Issue/PR/Release/Tag 全覆盖、GitHub App 全套 OAuth、任意仓库语义索引、原生微信按钮、向量数据库、复杂重复习惯规则与健康分析、每日自动推送简报、语音/头像动画、移动 App、多租户 SaaS 计费，均不作为 MVP 完成条件。

## Non-Goals

不开放修改代码、外部部署、邮件/付款/提交表单；不提供通用浏览器与 shell；不让人格提示覆盖系统权限；不承诺看见线下生活；不承诺未经接入核验的普通个人微信收发能力。

## Open Questions

批准本方案前：接受建议范围、部署预算与默认交互；可在一次统一反馈中修改。开发开始前：确认本人企业微信管理员条件、域名/服务器与 Token Factory 账户，凭据通过本地环境配置，不在聊天粘贴。开发第一阶段实测：模型结构化输出、微信可信 IP 与收发、Vercel 生产域名/日志权限。无法通过时明确改范围并更新 PRD，不隐瞒关键能力缺失。
